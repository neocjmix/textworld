# 트래픽 수준에 따른 구현 단계

2026-11-16. **현재 할 일은 1단계다.** 기존 분산 설계는 성장 이후의 방향으로 유지하고, 당장 두 세계 서버·CRDT·자동 오케스트레이션을 만드는 순서는 변경한다. 이 문서는 구현 순서에 관해 [최종 구조 제안](FINAL_ARCHITECTURE_PROPOSAL.md)과 [Railway 배치안](RAILWAY_SCALE_OUT.md)보다 우선한다. 운영 코드와 제품 헌법은 이번에 변경하지 않았다.

2026-11-18 구현 및 재측정 결과는 [1단계 검증 기록](STAGE1_VERIFICATION.md)에서 확인한다. 아래 11월 16일 수치는 개선 전 기준이다.

## 단계 요약

아래 인원은 **설계 검토를 위한 규모 예시이며 수용 인원 보장이 아니다.** 접속자 수와 실제 활동자 수를 구분한다. 1,000명이 읽는 경우와 100명이 계속 입력·이동하는 경우의 병목은 다르다. 단계 진입은 인원 숫자보다 측정된 병목으로 결정한다.

| 단계 | 트래픽의 모습 | 도입할 구조 | 다음 단계의 근거 |
| --- | --- | --- | --- |
| **1. 단일 서버를 안정화 — 지금** | 현재의 소수~수십 명. 이후 100명 수준까지 단계적으로 부하를 올려 한계 측정 | 앱 1개·SQLite 유지, 짧은 변경 묶음, 시야별 갱신, 만료/이력 정리 | 지연이나 대기열이 지속적으로 늘어나는 원인이 확인됨 |
| **2. 관객 증가 대응** | 수백~수천 접속자가 같은 내용을 보는 형태. 실제 입력자는 상대적으로 적음 | 세계 처리 1개 + 접속 서버 2개부터. 필요량을 보고 수동 증설 | 전송을 분리했는데도 세계의 쓰기/정리 처리 자체가 포화 |
| **3. 활동자 증가 대응** | 수백~수천 활동자가 여러 공간에서 계속 입력·이동하는 형태 | 세계 처리 2개부터 공간 분할. 처음에는 고정 배치와 수동 증설 | 공간 재배치와 용량 변경을 운영 중 반복해야 함 |
| **4. 부하 변동의 자동 운영** | 절대 인원과 무관하게 피크/유휴 차이가 크고 수동 용량 조절이 반복됨 | 계측 기반 자동 확장 제어기, 자동 구역 배치·인계 | 자동화의 자원 절감과 운영 안정성이 비용보다 큰지 검증 |

2단계와 3단계는 항상 순서대로 할 필요가 없다. 입력 처리 병목이 먼저 나타나면 필요한 접속 경계만 만들고 3단계로 진행한다. 안정된 고정 용량으로 운영할 수 있으면 4단계는 계속 보류할 수 있다. 단계는 인원이 늘 때마다 자동으로 실행하는 마이그레이션 규칙이 아니다.

## 현재의 증거

[기존 측정](CAPACITY_2026_11_16.md)은 같은 지역의 32명이 초당 1자씩 입력했을 때 ACK p95가 약 6~7초로 밀렸음을 보여준다. 해당 조건에서 입력당 저장 평균은 약 1ms, 관측/전파는 약 44ms였다. 이것을 모든 조건에서의 동접 32명 한계로 일반화하지 않는다.

자동 크기 변경에는 수백 ms의 동기 처리 사례가 있었고, 현재 글자가 만료돼도 history/operations는 남았다. 따라서 배포 인스턴스부터 늘리기 전에 반복 전파, 이벤트 루프 중단, 무기한 기록이라는 확인된 원인을 해결해야 한다. 개선 후의 수용 인원은 아직 측정하지 않았다.

## 1단계 — 앱 1개를 유지하며 불필요한 반복과 무제한 누적을 제거

Railway 서비스 1개·볼륨 1개, Node.js와 SQLite를 유지한다. 책임은 코드 안에서 입력 처리·변경 전달·정리로 나누되, 아직 프로세스 간 RPC나 별도 브로커를 도입하지 않는다.

지금 구현할 범위:

1. **변경 묶음 전달.** 입력은 도착할 때 처리하고 관측 변경은 우선 50ms 동안 모은다. 같은 칸의 중간 변경과 개별 커서 이동도 모두 포함한다. 크기 상한을 넘으면 나눠 보내고, 임의 생략으로 처리량이 좋아졌다고 계산하지 않는다. 수신자는 변경들을 적용한 뒤 화면을 그린다.
2. **변경된 시야만 갱신.** 작은 공간별 구독 목록을 두고 변경이 있는 곳만 보낸다. 모든 입력마다 모든 사용자의 전체 시야와 전체 커서 목록을 다시 만들지 않는다. 같은 본문의 계산·인코딩을 공유한다. 시야 밖 글자는 브라우저·봇에 보내지 않는다.
3. **만료와 기록의 수명 제한.** 약 3분 글자 만료를 유지한다. history, 중복 방지, 삭제 표식, 재전송 정보의 유효 범위를 정한다. 오래된 기록을 지워도 중복 쓰기가 다시 실행되거나 옛 글자가 부활하지 않도록 세션 순번/거부 기준과 함께 바꾼다. 작은 작업 단위로 정리하고 저장된 글자보다 과거 기록만 계속 커지는 현상을 막는다.
4. **크기 변경의 중단 시간 관리.** resize와 만료가 입력을 막는 시간을 측정한다. 지연 기준을 넘는 구간은 계산을 나누거나 별도 실행하고, 동시에 들어온 입력과 커서 보정이 안전한지 검사한다. 전체 분산 좌표 인덱스를 지금 도입하지 않는다.

나중에 재사용할 것은 입력 의도와 공개 변경 기록의 경계, 구독 목록, 계측이다. 사용하지 않는 분산 프레임워크나 범용 추상화까지 미리 만들지 않는다. 기존 한국어 IME·CJK 두 칸·로컬 예측·사람/봇 행동 제한은 유지한다.

**완료/유지 판단:** 8/16/32/64/128 연결처럼 점진적으로 올리되 읽기 중심·혼합 입력/이동·한 지역 집중을 나눠 측정한다. 현재 예상 피크와 그 1.5배의 정상 행동 부하에서 대기열이 계속 늘지 않고, 지연·만료·저장량 조건을 만족하면 이 구조를 유지한다. 이 수치는 시험 순서와 여유 목표이며 각 인원의 지원을 약속한 것이 아니다.

## 2단계 — 관객과 연결이 병목일 때 접속 처리 분리

진입 조건은 세계의 입력/저장은 여유가 있는데 연결 유지·관측 인코딩·전송이 지연의 주원인인 경우다. 최종 인터넷 송신 바이트만 부족한 경우에는 접속 서버 추가로 비용이나 클라이언트 대역폭이 사라지지 않는다는 점도 구분한다.

Railway에는 세계 상태/참여자 권위 서비스 1개와 볼륨 없는 gateway를 둔다. gateway는 replicas 2개부터 실제 측정에 맞춰 수동으로 늘린다. 세계는 변경 묶음을 gateway에 공유하고 gateway가 자기 접속자에게 전달한다. 초기에는 직접 연결한 내부 스트림과 짧은 기록으로 시작하며 Redis·NATS·Centrifugo의 도입을 선행 조건으로 만들지 않는다. 기존 제품을 쓸 실익이 확인되면 해당 경계에서 비교한다.

HTTP/MCP 세션, 커서, 순번과 속도 제한의 권위는 세계 서비스에 남긴다. 어느 gateway로 재접속해도 같은 권위를 찾도록 한다. 세계 DB와 상태를 gateway마다 복제해서 별개 세계를 만들지 않는다.

서로 다른 gateway에 연결된 두 브라우저, gateway 재시작, 느린 독자, 중복/이어받기, 사람과 봇의 동일 제한을 검증한다. 이 단계에서 해결되는 것은 연결·관측 전달 용량이며, 세계 상태를 확정하는 서버는 하나라는 한계가 남는다.

## 3단계 — 실제 입력 처리와 살아 있는 상태를 공간별로 분산

진입 조건은 반복 관측을 제거하거나 분리한 뒤에도 세계의 쓰기·만료·상태량이 한 처리자의 한계에 가까워지고, 여러 공간을 나눠 처리하면 개선할 근거가 있는 경우다.

[A안](FINAL_ARCHITECTURE_PROPOSAL.md)의 세계 worker를 2개부터 도입한다. 한 worker가 여러 논리 구역을 맡고, 각 구역에는 유효한 담당자 하나가 있다. 처음에는 고정된 담당표와 수동 증설/이전을 사용한다. Railway의 볼륨 제약에 따라 로컬 저장소를 가진 worker들은 별도 서비스로 배치한다.

분산을 시작하는 순간 필요한 정확성은 뒤로 미루지 않는다. 경계의 두 칸 글자, 자기 입력 순서, 중복 처리, 배치 변경 중 커서 보정, 담당자 세대와 옛 담당자의 쓰기 차단, 저장/변경 발행의 복구를 검증한다. 자동 오케스트레이터가 없어도 수동 이전은 안전해야 한다. 고가용성과 자동 장애 전환의 수준은 가용성 요구에 맞춰 따로 정하고 검증한다.

여러 공간의 동시 쓰기와 반복 확장/축소가 필요해지면 좌표와 저장 주소 분리도 이 단계에서 적용한다. 1단계의 큰 resize만으로 이미 지연 기준을 넘으면 그 원인에 필요한 부분을 먼저 해결할 수 있다. 트래픽 단계가 세계 크기 문제의 해결을 막는 규칙은 아니다.

실제 Railway 인스턴스 1/2/4/8개에서 동일 단위 부하를 추가해 처리량 효율·지연·비용을 비교한다. 첫 50ms 관측 조건의 내부 관측 지연 p95 100ms 이내와 처리량 효율 80% 이상은 검증 목표다. 아직 달성한 수치가 아니다. 특정 한 칸에 모두 쓰는 경우는 공간 분산 부하와 별도로 보고한다.

## 4단계 — 검증한 수동 운영을 자동화

단순히 특정 동접 수가 되었다는 이유로 도입하지 않는다. 수동 증설/축소와 구역 재배치가 반복되고, 피크 대비 여유 자원의 비용이나 대응 지연이 실제 문제가 될 때 도입한다.

처음에는 제어기가 측정값으로 결정만 기록하도록 하고 운영자의 수동 조치와 비교한다. 이후 준비 완료 확인과 안전한 인계가 검증된 증설부터 자동화하고, 충분히 검증한 뒤 축소를 연결한다.

규칙에는 최소/최대 인스턴스, 비용 상한, 지속된 부하 조건, 증감 사이 대기 시간, 중복 명령 방지, 진행 중 이전의 복구를 둔다. Railway API는 실제 자원 생성을 맡고, Textworld 제어기는 목표 용량과 공간 배치를 관리한다. 글자 입력/만료의 시간이나 관측 계약을 몰래 완화하는 방식으로 부하를 낮추지 않는다.

## 인원수와 별개로 다룰 분기

- **한 칸의 극단적인 쓰기 집중:** A안의 상태 확정이 실제 병목이면 B안의 서버측 셀 CRDT를 비교한다. Yjs Map/업데이트 병합을 기준점에 포함한다. 관측 계약이 같으면 수신 바이트가 자동으로 감소하는 것은 아니다. CRDT는 모든 규모에 공통으로 거쳐야 하는 단계가 아니다.
- **가용성:** 작은 서비스라도 재시작 중단을 허용할 수 없으면 복제/전환 검증을 앞당길 수 있다. 접속자 수만으로 고가용성 요구를 정하지 않는다.
- **세계 크기:** 큰 세계의 주소/resize 비용과 사용자의 활동량은 별도다. 필요한 인덱스 개선을 분산 서비스 개수와 묶어서 한꺼번에 도입하지 않는다.

## 다음 단계로 넘어갈 측정 기준

초기 성능 목표는 50ms 묶음 설정에서 **입력 수신 후 서버의 변경 전송 준비까지 p95 100ms 이내**, 대기열의 지속 증가 없음, 정상 구독 중 공개 변경 누락 없음이다. 이 내부 목표와 실제 브라우저 ACK/관측 왕복 지연을 구분해서 보고한다. 인터넷 지연이 목표에 포함된다고 설명하지 않는다.

예상 피크와 그 1.5배를 같은 시야·정상 행동 제한·관측 주기로 비교한다. 실패하면 먼저 어느 비용이 증가했는지 확인한다. 관측 CPU/연결이 원인이면 2단계, 세계 쓰기/정리/상태량이면 3단계, 반복되는 운영상 용량 변경이면 4단계를 검토한다. 충분한 여유가 있으면 현재 단계를 유지한다.

1시간 지속 실행에서 글자 만료 지연과 메모리/저장량이 안정되는지 확인한다. SQLite 파일이 삭제 직후 작아지지 않는 것과 빈 페이지를 재사용하지 못해 계속 증가하는 것을 구분한다. 재전송 보관 범위를 넘은 reset, 429, 서버 오류, 연결 종료와 미처리량도 성공한 처리량 옆에 함께 기록한다.

[기존 계측](MEASUREMENTS.md)을 활용하고 부족한 신호를 추가한다. 서버별 작업/전송량, 활동자 비율, 정상 부하 지연, 시간당/활동 세션당 자원 비용을 남긴다. 원시 글자·위치·개인 식별자를 측정 로그로 수집하지 않는다. 1단계가 끝난 뒤 실측으로 각 단계의 계획 인원 예시를 갱신한다.

## 지금의 작업 범위

**변경 묶음 → 시야별 갱신 → 만료/이력과 resize 중단 시간 → 같은 조건의 재측정** 순서로 진행한다. API와 화면 동작을 유지하면서 바꿀 수 있는 작은 단위로 나눈다. 지금은 세계 서버 증설·범용 CRDT 도입·자동 오케스트레이터·별도 메시지 브로커를 구현 범위에 넣지 않는다.

이 문서 추가는 계획 변경이다. 단일 서버 개선이나 새로운 수용 인원 검증을 이미 완료했다고 주장하지 않는다. 이전 분산 의미 모형과 두 WebSocket의 묶음 전송 실험은 참고 자료이며 실제 앱 적용 이후의 회귀·부하 검사를 대체하지 않는다.
