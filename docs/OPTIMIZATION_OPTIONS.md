## 전송 경로를 바꾸는 네 가지 안

| 경로 | Textworld에서 쓸 자리 | 성립 조건 |
| --- | --- | --- |
| 바이너리 WebSocket | 현재 Railway 한 대에서 권위 있는 글·삭제·커서 변경을 작은 순서열로 보낸다. 구현비가 가장 낮은 비교 기준이다 | 연결별로 보내는 바이트는 계속 과금된다. 모바일 손실 환경에서 큰 스냅샷 뒤의 글이 얼마나 밀리는지 잰다 |
| 버전이 붙은 구역 데이터와 HTTP 캐시 | 접속·복구 시 반복되는 공개 영역의 스냅샷을 캐시하고 실시간 변경과 개인 응답은 기존 연결로 보낸다. 여러 독자에게 같은 원본을 배포하는 스트리밍 서비스의 방식이다 | 승인된 시야에 들어온 부분만 받을 수 있어야 한다. 캐시 경계, 적중률, 작은 요청 비용, CDN 실제 청구를 함께 본다 |
| WebTransport / HTTP/3 | UDP 기반 QUIC에서 확정 변경과 큰 스냅샷을 독립적인 신뢰 스트림으로 보낸다. 데이터그램에는 사라져도 복구할 필요가 없는 화면 미리보기만 싣거나, 유실된 확정 순번을 신뢰 스트림으로 채운다 | 손실 난 모바일 회선에서 한 스트림의 재전송이 다른 스트림을 막는 시간을 줄일 수 있다. 같은 본문을 같은 수신자에게 보내는 비용은 남는다. Railway 공개 입구는 HTTP/1.1·HTTP/2·TCP를 지원해 이 구성에는 HTTP/3 종단이 별도로 필요하다 |
| WebRTC DataChannel P2P | Railway에 입력 판정과 접속 상대 소개를 두고, 서버가 서명한 같은 구역 묶음을 그 구역을 보는 독자가 다른 독자에게 중계한다. 브라우저끼리 직접 연결되는 경로에는 Railway에 공개 UDP 포트가 필요하지 않다 | 시야 중첩, 연결 유지 시간, 직접 전달 바이트, 중계자의 업로드와 지연, TURN·서버 보충 비용에 따라 성패가 갈린다 |

일반 웹페이지에서 UDP 계열을 쓰는 선택지는 WebTransport나 WebRTC다. 글을 빠짐없이 받는 기능은 WebRTC의 신뢰형 순서 보장 데이터 채널로도 제공할 수 있다. UDP는 한 번 보낸 글을 인터넷의 모든 독자에게 자동 복제해 주지 않는다. [WebTransport](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API) · [WebRTC 데이터 채널](https://www.rfc-editor.org/rfc/rfc8831.html) · [Railway 공개 네트워크](https://docs.railway.com/networking/public-networking/specs-and-limits) · [Railway의 인바운드 UDP 안내](https://station.railway.com/feedback/allow-outbound-udp-traffic-0f74101c)

### P2P가 경제적일 수 있는 조건

1. **서버가 판정하고 독자가 나눠 보낸다.** 입력과 429, 덮어쓰기 순서, 버전을 확인한 삭제와 지도 크기는 서버에서 확정한다. 먼저 같은 내용을 충분히 오래 보는 독자들끼리 한 단계만 중계한다. 초기에는 원하면 참여하는 독자 중 업로드 여유가 있는 경우로 한정한다. 개인 응답·경계 셀은 서버 경로를 쓴다.
2. **중계자가 떠나도 같은 글을 받는다.** 수신자는 서버의 서명과 허용 구역·지도 버전·연속 순번을 확인한다. 중복은 버리고 빠진 범위는 짧은 서버 이력으로 보충한다. 다른 독자가 본문을 바꾸거나 고의로 누락해도 세계 상태가 바뀌지 않도록 한다. 모바일이 백그라운드로 가는 경우, 연결 협상 시간, 상대에게 공인 IP가 드러날 수 있는 점과 업로드 비용이 참여 가능 비율에 영향을 준다. [WebRTC IP 처리](https://www.rfc-editor.org/rfc/rfc8828.html) · [TURN 중계](https://webrtc.org/getting-started/turn-server)
3. **직접 연결 성공률보다 절감한 유료 바이트를 본다.** 예를 들어 공통 형식만으로 전체 실시간 바이트가 4분의 1이 된다고 가정해도 주 $39.31이다. 목표 $13.33까지는 남은 유료 전송비를 66% 더 줄여야 한다. 광장 시간대의 모든 실시간 송신을 무료로 만드는 이상적인 경우에도, 같은 4배 가정에서 분산 시간대의 실시간 송신만 주 $22.73이다. 흩어진 사용자 사이에도 공유 가능한 데이터가 얼마나 되는지부터 구한다. 4배는 예시이며 실측값이 아니다.
4. **서버 없는 모델도 별도 대안이다.** 모든 사람이 직접 연결되는 완전 연결망은 광장 250명에서 연결 31,125쌍이다. 작은 중계망을 만들면 연결 수는 줄어든다. 글 확정까지 피어에 맡기면 접속 교체·망 분리 중 쓰기 순서, 지역 접근·429 판정, 만료와 지도 버전 합의를 새로 해결해야 한다. P2P의 경제성을 시험한다면 서버가 확정하고 독자가 한 단계 중계하는 안을 우선한다.

## 계속할지 결정하는 실험

1. **먼저 1~2인일을 배정한다.** 기존 900/80/20 조건의 합성 기록에서 글·커서·밝기·실제 삭제·확장·입장별 바이트와 CPU 시간을 나눈다. 같은 기록을 간결한 형식으로 오프라인 재생하고 모든 수신자의 관측 순서를 대조한다. 같은 시각에 허용된 같은 내용을 보는 독자들의 체류 시간을 이용해 직접 연결이 항상 성공한다고 가정한 P2P 절감 상한도 구한다. 합성 글·시드로 재현하고 실제 사용자의 글이나 위치를 로그에 남길 필요는 없다.
2. **돈과 지연을 따로 판정한다.** 필수 본문, 접속·복구 데이터, 정적 자산과 서버를 합친 비용이 낙관적인 공유 조건에서도 목표를 넘으면 해당 월 예산을 위한 개발을 중단한다. 상한에서 여유가 있으면 효과가 큰 한두 후보만 구현한다. P2P가 필요한 경우 서로 다른 가정망·이동통신망·TURN 경로에서 손실·중계자 이탈을 넣고 유료 바이트와 실제 수신 지연을 비교한다.
3. **통과 후보만 1시간 확인한다.** 분산과 광장, 실제 시계·만료·확장·축소, 접속자 교체를 켜고 동접 1,000명과 피크 1,500명을 나눠 본다. 기존 목표는 서버 전송 준비 p95 100ms와 정상 시야 누락 0이다. 이번 판정에는 로컬 타인 수신 p95 200ms, 10초 내 교체 접속 성공률 99% 이상을 제안한다. 실제 연결 수, 정리 적체, 모바일 화면 표시, 외부 송신 계량도 함께 확인한다. 월 $100이 운영의 필수 조건이면 대표 부하에서 돈과 품질을 함께 충족한 구성만 채택한다.
