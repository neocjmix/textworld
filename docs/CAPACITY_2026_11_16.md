# 현재 구조의 수용 규모와 병목 — 2026-11-16

현재 형태는 활발한 참여자 10여 명, 활동 비중이 낮은 수십 명의 작은 세계를 운영하는 단계로 보는 것이 타당하다. 수백~수천 명이 활발하게 움직이고 입력하는 서비스의 수용 능력은 확보하지 못했다. 아래는 제품 지원 인원 보장이 아니라 현재 코드의 짧은 로컬 실험과 운영 자원 관측에 근거한 판단이다.

운영 애플리케이션은 `29045ba95c0f2031cfd726a6dbb5971b71c8c058`, Railway 배포 `ec909614-2f58-4291-b16e-10f6460b0e05`다. 이 조사에서는 애플리케이션 코드를 변경하지 않았으며, 운영 서버에 부하나 테스트 글자를 넣지 않았다. 별도 로컬 실험 스크립트와 측정 결과를 추가했다.

## 운영에서 확인한 것

- Railway `production`, `us-west2`, 서버 1개, 영구 볼륨 1024MB. CPU/RAM 설정 한도는 8코어/8GB이며 예약 자원이나 단일 JS 스레드의 병렬 처리량을 뜻하지 않는다.
- 최근 7일의 1시간 간격 표본 169개: CPU_USAGE 평균 약 0.00286, 메모리 평균 0.096GB·표본 최대 0.160GB, 디스크 현재 약 0.062GB. [원자료](measurements/platform-capacity-2026-11-16.json).
- 조사 중 공개 `/health`는 정상, 세계 32×16·epoch 220·현재 참여자 0명이었다. 소수 이용 또는 유휴 상태의 자원 관측으로 포화 성능을 추정하지 않는다. 시간별 표본은 순간적인 지연이나 피크를 놓칠 수 있다.
- 관리용 앱 통계 토큰은 서비스에 설정돼 있지만, 새 실행 환경에 비공개 사본이 없고 Railway OAuth는 변수 값 조회를 허용하지 않는다. 따라서 이번에는 누적 앱 통계의 실제 동접·입력량·ACK 지연을 읽지 못했다. 계측 저장 실패가 있었다는 뜻은 아니다.

## 실제 WebSocket 부하 실험

서버와 부하 생성기를 별도 Node 프로세스로 실행했다. 서버는 실제 파일 SQLite의 WAL·`synchronous=FULL`, 원래의 참여자 속도/시야 제한과 관측·JSON 전파 경로를 사용한다. 여러 네트워크의 참여자를 흉내 내기 위해 클라이언트별 loopback 출발 주소를 사용하며, 운영의 동일 IP 제한을 변경하지 않는다.

AMD EPYC 9V74, Node 24.22.1, 로컬 cgroup 4코어 한도다. Railway의 CPU·디스크·TLS·인터넷·브라우저 렌더링을 재현한 시험은 아니다. 세계는 512×256, 시야 160×48, 흩어진 ASCII 약 10,083개로 시작한다. 모든 참여자는 같은 지역에서 시작하며 기본 시야 밀도는 약 7.8%다. 입력은 커서 프로토콜의 `type`으로 한글 한 글자씩 덮어쓴다. native DOM·IME 비용은 포함하지 않는다.

초기 글자는 행별 묶음으로 저장했다. 각 글자가 서로 다른 변경 번호를 가진 실제 세계와는 색·신선도 표 크기가 다를 수 있다. 모바일의 작은 시야, 다른 위치에 흩어진 참여자, 오래 누적된 이력, 접속 폭증도 이 표와 같은 조건이 아니다.

각 경우에 12초 동안 ACK를 기다리지 않고 정해진 빈도로 요청을 보낸다. 예정 시각과 실제 송신 시각을 따로 기록해 서버가 느려질 때 생성기의 제공량까지 줄어드는 오류를 피한다. 송신 지연 p95는 약 2~2.4ms였다. 전송 종료 시 미처리 수와 추가 배출 시간을 기록한다. 세계 시계는 고정해 정상 상태의 전파 비용을 분리했으며, 자동 resize·만료 부하는 이 표에서 제외했다.

| 동접 | 실제 입력하는 사람 | 1인당 입력 | 서버 ACK p95 | 서버 평균 CPU 코어 | 12초 종료 시 미처리 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 8 | 8 | 초당 1자 | 27.5ms | 0.15 | 0 |
| 8 | 8 | 초당 3자 | 24.0ms | 0.37 | 0 |
| 16 | 16 | 초당 1자 | 41.8ms | 0.45 | 0 |
| 32 | 32 | 초당 1자 | **6,137~6,986ms** | 1.01~1.02 | **111~124** |
| 64 | 6 | 초당 1자 | 150.0ms | 0.67 | 0 |
| 128 | 6 | 초당 1자 | **1,778.1ms** | 1.09 | **7** |

32명 조건은 포화를 확인하기 위해 두 번 실행했고, 입력을 멈춘 뒤에도 약 4.9~5.6초 더 처리해야 했다. 최악 ACK는 약 10~11초였다. 나머지 조건은 단일 짧은 실행이다. 8명·3자 조건이 1자 조건보다 p95가 작다고 해서 부하가 늘면 빨라진다는 뜻은 아니다. 짧은 실행의 JIT·GC·호스트 편차가 있다.

추가로 글자가 시야의 33.3%를 채운 경우 8명/8자·초와 16명/16자·초의 p95는 각각 51.1ms, 54.9ms였고 CPU는 0.25, 0.78코어였다. 8명 중 2명이 초당 10회 커서를 움직이는 경우 p95는 18.9ms, CPU 0.28코어였다. 이동도 전파 비용을 발생시킨다.

10개 실행의 ACK는 모두 배출됐고 프로토콜 오류·429·연결 끊김은 없었다. **429가 없다고 과부하가 없다는 뜻은 아니다.** 사용자별 행동이 정상 속도여도 합산 작업량은 단일 스레드를 포화시킬 수 있다. 입력자는 로컬 예측으로 먼저 글자를 보므로 여기서 측정한 ACK를 첫 화면 표시 시간으로 해석하지 않는다.

## 어디서 시간이 쓰이는가

핵심은 [presence 전파](../server/index.js)와 [Observer.read](../server/visibility.js)다. 글쓰기와 커서 이동마다 모든 브라우저 참여자의 전체 시야를 읽고, 현재 셀·색·신선도·주변 참여자를 계산하고, 이전 결과와 비교한다. 시야 밖 사건으로 응답이 생기지 않더라도 그 비교 계산은 수행한다. 주변 참여자 필터도 전체 참여자 목록을 훑는다.

32명·초당 합계 32자 조건에서 쓰기 저장은 평균 약 **0.97ms**, 전체 관측·전파는 입력 한 번당 평균 **44.3ms**였다. 12초에 시야 계산 **12,288회**가 발생했다. 입력 384개 × 참여자 32명이다. 두 번째 실행에서도 포화가 재현됐다. 현재 가장 먼저 손댈 부분은 SQLite 교체가 아니라 이 반복 계산과 전파다.

참여자 수와 활동자 수를 각각 N, A라 하면 시야 재계산 횟수는 대략 N×A×행동 빈도에 비례한다. 모두 비슷하게 활동하면 이 부분만 N²로 늘어난다. 전체 참여자 목록을 반복해서 필터·정렬·직렬화하는 비용이 추가된다. 같은 장소에 모인 경우 주변 커서 목록과 색·신선도 표의 반복 전송도 커진다. 128명 중 6명 입력 조건에서 전체 수신 application JSON은 약 138MB였다. 헤더·TLS·인터넷 청구량을 측정한 값은 아니다.

기존 엔진+관측 microbenchmark 72개 경우도 현재 코드로 다시 실행했다. 점유 8,192·시야 160×48에서 쓰기 한 번과 전원 갱신의 반복별 p95 중앙값은 관측자 1명 2.82ms, 8명 23.97ms, 32명 98.02ms였다. WebSocket 실험과 시야 배치·저장소·실행 방식이 다르므로 수치를 직접 합치지 않는다. 이전 Xeon 측정과도 하드웨어가 달라 성능 개선률을 계산하지 않는다. [원자료](measurements/scaling-current-2026-11-16.json).

## 텍스트와 세계 크기

현재 크기의 코드상 상한은 **1024×512 = 524,288칸**이다. 빈 공간은 셀 객체로 모두 저장하지 않고, 일반 관측은 시야 범위만 읽으므로 세계가 넓어지는 것 자체가 모든 읽기를 전 세계 탐색으로 만들지는 않는다.

| 최대 세계에서의 밀도 | 점유 칸 | 전부 영문인 경우 | 전부 한글·전각인 경우 |
| --- | ---: | ---: | ---: |
| 목표 8% | 약 41,943 | 약 4.2만 글자 | 약 2.1만 글자 |
| 상단 기준 12.5% | 65,536 | 약 6.6만 글자 | 약 3.3만 글자 |

이는 설정으로 계산한 공간 규모이며 성능 보장이나 글자 입력 거부 한도가 아니다. 최대 크기 이후에는 더 확장되지 않고 밀도가 높아질 수 있다. 모든 칸을 채우면 물리적으로 영문 52만 글자/전각 26만 글자에 해당하지만, 그 상태를 운영 목표로 삼거나 쾌적하다고 보장할 근거는 없다.

자동 확장에서는 공백 경로 검색·재배치 계획·전체 셀 테이블 교체가 동기 실행된다. 참가자 0명, ASCII 약 1/7 밀도, 실제 파일 SQLite로 각 3회 실행한 한 단계 자동 확장 비용은 다음과 같다.

| 확장 전 세계 | 표시 칸 | 한 단계 확장 시간 범위 |
| --- | ---: | ---: |
| 128×64 | 1,171 | 10.8~28.2ms |
| 512×256 | 18,725 | 113.0~166.6ms |
| 896×448 | 57,344 | **282.6~433.3ms** |

모두 글자 손실 없이 확장했지만, 서버 이벤트 루프는 이 시간 동안 다른 입력을 처리하지 못한다. 참여자의 커서 보정·전체 snapshot 전송 비용은 이 수치에 포함하지 않았다. 타이핑을 계속 허용하는 커서 모델과 계산을 병렬로 실행하는 것은 별개다. [원자료](measurements/world-cost-2026-11-16.json), [재현 스크립트](../experiments/world-cost.mjs).

## 3분 만료가 해결하지 않는 두 가지

1. **정리 처리량:** 만료 후보는 5초당 최대 500글자다. 두 칸 문자의 head 하나를 한 글자로 센다. 정상 주기 기준 초당 약 100글자이며, 이벤트 루프가 밀리면 더 낮다. 서로 다른 위치에 새 글자가 이보다 빠르게 계속 쌓이고 덮어쓰기·재배치 삭제가 이를 상쇄하지 않으면 적체 때문에 3분 만료를 지키지 못한다.
2. **영구 저장량:** `history`, 중복 처리용 `operations`, 시간/작성자 표의 보존 기간이 없다. 셀 만료는 과거 이력을 제거하지 않으며, 빈 tombstone도 다음 재배치까지 남을 수 있다. 세계가 작고 현재 글이 적어도 DB는 계속 커질 수 있다.

한 칸의 한글을 5,000번 덮어쓴 로컬 실험은 표시 글자가 1개인 동안 DB 약 6.25MB를 사용했고, 만료 후 글자 0개가 되어도 크기가 유지됐다. history 10,002행·operations 5,001행이 남았다. UUID 기반 실제와 유사한 식별자를 사용한 이 경우 추가 저장량은 1회 확정당 약 1,237바이트였다. 같은 형태의 입력이 초당 10회 지속된다는 조건으로 단순 환산하면 하루 약 1GB다. 입력 묶음 크기·이력·인덱스 상태에 따라 달라지며 실제 운영 증가율 예측은 아니다. 현재 1GB급 볼륨에서 활동량이 커지면 중요한 제한이 된다.

## 측정이 요구하는 설계 조건

1. **변경된 범위에 해당하는 구독자만 갱신하고, 셀·presence 변화분을 전송한다.** 동일/겹치는 시야 계산을 공유하고 짧은 주기로 변경을 합치는 방식과 비교한다. 한곳에 모인 사람들은 모두 수신해야 하지만, 매 입력마다 전체 시야를 재구축할 필요는 없다. 여기서 수십 명 포화와 통신 증폭을 먼저 줄인다.
2. **만료·이력 비용을 제한한다.** 공유 시간 표식을 활용한 만료 큐, 시간 예산에 맞춘 배치, 명시적인 history/중복 기록 보존 기간을 검토한다. 사용자가 요구한 경제적인 시간 표현을 유지한다.
3. **크기 변경 계산을 나누거나 별도 실행한다.** 계산량·중단 시간을 제한하고 현재 커서 보정·동시 입력 의미를 유지하는 것이 목표다. 무조건 트랜잭션을 제거하는 해결책은 아니다.
4. **이후 공간별 처리 책임과 연결/구독 처리를 나눈다.** 지금은 메모리 셀·참여자·순서 권위가 한 프로세스에 있고 SQLite 파일도 단일 writer 전제다. Railway replica 수를 늘리는 것만으로 같은 세계가 선형 확장되지 않는다. 연결 분산만으로는 관측 계산과 쓰기 권위가 분산되지 않는다.

위 항목은 현재 구조에서 확인한 제약이다. 구현 순서는 [트래픽 수준별 단계](SCALING_ROADMAP.md)를 따른다. 먼저 단일 서버에서 변경 묶음·시야별 갱신·저장 수명과 resize 중단 시간을 개선하고 같은 조건으로 재측정한다. 관객/연결이 병목이면 접속 처리를, 세계 쓰기/정리/상태량이 병목이면 공간별 처리를 분리한다. [MMO를 참고한 분산 세계 설계](DISTRIBUTED_WORLD_DESIGN.md)는 이후 구조의 방향으로 유지한다. 기존 측정값은 그대로이며 개선 후 수용 인원은 아직 검증하지 않았다.

## 재현

```sh
npm ci
npm run bench:scale
node experiments/capacity.mjs
node experiments/world-cost.mjs

# 포화 조건 재실행 또는 활동 빈도 변경
CAPACITY_CASES='[{"peers":32,"active":32,"rate":1,"layout":"uniform","action":"type"}]' node experiments/capacity.mjs
```

모두 로컬 전용이다. 성능 실험끼리는 동시에 실행하지 않았다. 데이터 산출물은 `artifacts/`에 기록하며, 이 문서가 참조하는 고정 결과는 `docs/measurements/`에 보존했다. 서버·브라우저 코드와 제품 헌법은 변경하지 않았다.
