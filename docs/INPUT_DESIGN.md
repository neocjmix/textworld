# 공간 입력 인터랙션 재평가

2026-11-02. Enter를 포함한 입력 동작을 제품 목적과 사용자가 만드는 글의 모양을 기준으로 다시 평가한다. 같은 날 보고된 한글 낱자 분리, CJK 문자 폭, 관성 스크롤 요구를 아래 조합·폭·탐색 규칙에 반영했다. 제품 헌법은 변경하지 않는다. 기존 동작을 유지하는 것이 목표가 아니며, 아래 규칙은 구현이 쉬운 키 이벤트보다 사용자의 작성 의도를 우선한다.

## 판단 기준

Textworld의 사용자는 같은 공간의 특정 위치에 글을 놓는다. 문장은 여러 행에 걸칠 수 있지만, 다른 글을 밀어내는 문서나 전송 버튼으로 완성되는 메시지는 아니다. 따라서 다음 조건이 중요하다.

1. `ABC`, Enter, `D`를 입력했을 때 다음 행의 `D`를 어디에 놓을지 예측할 수 있어야 한다.
2. 같은 내용을 한 번에 붙여넣거나, 여러 키 입력·IME 완료로 나누어 전달해도 같은 모양이 되어야 한다. 브라우저 이벤트 분할이 작품의 배치를 바꾸면 안 된다.
3. 이동은 이동, 글자 쓰기는 덮어쓰기, 삭제는 지우기로 구분한다. 줄바꿈만으로 기존 글자를 밀거나 지우지 않는다.
4. 커서의 화면상 중심 고정과 세계 좌표에서의 작성 기준은 별개다. 화면이 항상 중심을 따라가도 어디서부터 줄을 쓰고 있는지는 유지할 수 있어야 한다.
5. OS가 보낸 조합 확정·줄바꿈·삭제·치환·실행 취소 의도를 모두 단순한 새 문자 입력으로 해석하지 않는다.

## 기존 구현의 실행 반례

기준 구현 `f7a034a`의 `shared/world.js`를 Node에서 실행했다. 세계 크기는 128×64, 시작 위치는 `(10,10)`이다.

| 입력 경로 | 마지막 `D` 위치 |
| --- | --- |
| `writePlan('ABC\nD', 10, 10, world)` 한 번 | `(10,11)` |
| 먼저 `ABC`, 그 결과 위치에서 `\nD` | `(13,11)` |
| 키보드로 `ABC`, Enter, `D` | 기존 Enter 규칙에 따라 `(13,11)` |

같은 내용이 붙여넣기인지 연속 타이핑인지에 따라 다른 모양이 된다. Enter만 별도로 잘못 배치한 문제가 아니라 **지속되는 작성 의도를 입력 이벤트 하나의 시작 좌표로 대체한 문제**다.

기존 Enter는 `(13,10)`에서 `(13,11)`로 이동한다. 바로 Backspace를 누르면 `(12,11)`을 지운다. 사용자가 아직 아무 글자도 쓰지 않은 다음 행의 셀을 지우게 되며, 그 칸에 있던 다른 글도 영향을 받는다.

## Enter 모델 비교

| 모델 | `(10,10)`에서 `ABC` 뒤 Enter | 좋은 점 | 제품 목적·예상과의 충돌 |
| --- | --- | --- | --- |
| 현재 열 유지 | `(13,11)` | 좌표 규칙이 단순하고 아래로 이동하기 쉽다 | ArrowDown과 기능이 중복된다. 연속 문장의 왼쪽이 계단 모양으로 밀린다. 기존 paste와도 다르다 |
| 세계의 0열로 복귀 | `(0,11)` | 고정된 기준이 있다 | 토러스의 0은 저장 좌표상의 경계일 뿐 자연스러운 왼쪽 여백이 아니다. 다른 장소에서 쓰다가 멀리 이동한다 |
| 주변 글에서 행 시작 추론 | 추론한 열 | 기존 글 편집을 돕는 경우가 있다 | 공백·다른 사람의 글·조각난 글·동시 변경에 따라 기준이 달라진다. 같은 키가 다른 결과를 만든다 |
| Enter로 전송·입력 종료 | 위치 유지 또는 키보드 닫기 | 채팅·검색창에 익숙하다 | 글은 이미 셀마다 공유되고 있다. 보내야 할 메시지나 제출할 문서가 없고, 여러 행 쓰기가 어려워진다 |
| **현재 작성 기준 열로 복귀** | **`(10,11)`** | 짧은 문장·시·ASCII 배치의 행을 맞출 수 있다. 입력 방식과 이벤트 분할에 독립적인 규칙을 만들 수 있다 | 작성 기준을 임시 상태로 유지하고 언제 새로 정하는지 설명해야 한다 |

**선택: 현재 작성 기준 열로 돌아가 다음 행에서 계속 쓴다.** Enter는 carriage return과 다음 행 이동을 결합한다. 전역 문서의 행을 만들거나 셀을 삽입하지 않는다. 실제 한 칸 아래로만 이동하려면 ArrowDown이나 지도 탐색을 사용한다.

## 작성 기준의 수명

작성 기준 열은 현재 위치에서 글을 이어 쓰기 위한 임시 로컬 상태다. 소유한 게시물·문단·문서 경계를 만드는 것이 아니다.

모든 커서 이동에서 기준을 재설정하는 안도 다시 기각했다. `(10,8)`에서 `ABC`, ArrowLeft, `D`, Enter를 입력하면 사용자는 마지막 글자를 고쳐 `ABD`를 만든 것이다. 이때 기준이 ArrowLeft의 도착 열인 12로 바뀌면 다음 행이 `(12,9)`에서 시작한다. Enter만 고친 뒤 같은 오류를 교정 동작에 옮긴 셈이다.

| 기준 갱신 모델 | 결과와 판단 |
| --- | --- |
| 모든 이동에서 갱신 | 단순하지만 방향키로 오타를 고치면 행 정렬이 깨짐 |
| 모든 이동에서 유지 | 교정에는 맞지만 지도를 멀리 탐색해 새 글을 써도 이전 장소의 열로 돌아감 |
| 별도 명령으로만 기준 지정 | 명시적이지만 기본적인 여러 행 입력 전에 새 모드나 조작을 배워야 함 |
| **지도에서 새 장소 선택과 방향키 교정을 구분** | **새 장소에서는 새 기준을 잡고, 현재 글을 고치는 동안에는 기준을 유지. 이번 기본값으로 선택** |

- 지도 드래그·스크롤, GPS 이동, 공유 좌표 이동을 하면 그 위치에서 새로운 작성 기준을 잡는다.
- 첫 문자 또는 Enter로 작성 흐름이 시작된다. 그 전 방향키 이동은 현재 열을 예상 기준으로 삼고, 작성이 시작된 뒤 방향키 이동은 기존 기준을 유지한다.
- Home은 현재 행에서 작성 기준 열로 돌아간다. 방향키와 Home은 이전 작성 경로의 역추적 기록을 비운다. 임의로 이동한 뒤 Backspace가 과거 행으로 뛰지 않게 하기 위해서다.
- 글자 입력으로 자동 진행하는 커서, Enter, 알려진 작성 경로의 Backspace, Delete는 기준 열을 바꾸지 않는다. 경로 밖 Backspace도 활성 작성 기준은 유지한다. 아직 작성 전이라면 왼쪽 삭제 대상 셀을 새 예상 기준으로 삼는다.
- 지도 줌, 화면 크기 변경, 키보드 표시, 동일 위치 탭·포커스 복귀는 위치를 새로 선택한 일이 아니므로 기준을 유지한다.
- 같은 topology epoch에서 확인 대기 중인 쓰기 없이 재연결하면 작성 기준과 경로를 유지한다. 연결 중 서버가 주소 보존을 보장한 자동 크기 변경은 아래 조건을 모두 충족할 때 네이티브 문맥·미리보기·작성 경로도 유지한다. 전송 결과가 불확실한 단절, 일반 재동기화·오류 복구, 주소 보존을 확인할 수 없는 epoch 변경에서는 과거 문맥을 버리고 복구된 위치에서 다시 시작한다.
- 기준과 줄바꿈 복귀 경로를 영구 세계 데이터로 저장하지 않는다. 다른 사용자의 글·커서·추가 입력이 내 기준 열을 결정하지 않는다.

기준을 모르는 경우에는 현재 열이 새 기준이다. Enter와 Shift+Enter는 같은 공간 줄바꿈으로 처리한다. 문서의 soft break/hard break 구분을 별도로 도입하지 않는다.

## 입력 경로를 일치시키는 규칙

| 의도 | 처리 |
| --- | --- |
| 일반 문자, IME 완료, 붙여넣기의 문자 | 주소에서 글자 표시 폭 1칸 또는 2칸을 덮어쓰고 그 폭만큼 이동 |
| 키보드 Enter, Shift+Enter | 작성 기준 열의 다음 행으로 이동 |
| 모바일 `insertLineBreak` / `insertParagraph` | 같은 줄바꿈 동작 |
| 붙여넣기의 LF / CRLF / CR | 같은 줄바꿈 동작. CRLF는 두 번 이동하지 않음 |
| 여러 행 텍스트를 나누어 전달 | 동일한 작성 기준을 계속 사용 |
| 한글 조합 중 Enter | 우선 OS의 조합 확정. 같은 키를 새 줄바꿈으로 중복 실행하지 않음 |
| 방향키 | 한 셀 이동. 활성 작성 기준은 유지하고 역추적 경로는 비움 |
| Home | 현재 행의 작성 기준 열로 이동. 역추적 경로는 비움 |
| End | 정해진 공간 행 끝이 없으므로 미지원 안내. 임의의 경계로 이동하지 않음 |
| Delete | 현재 셀이 속한 글자를 비우고 위치 유지. 두 칸 문자는 두 칸을 함께 비움 |
| Backspace | 아래 작성 경로 규칙으로 이전 글자를 지우거나 줄바꿈 이동을 되돌림 |

클라이언트 예측과 서버의 실제 쓰기 계획이 같은 기준 열을 사용해야 한다. 프런트엔드에서만 Enter를 고치면 여러 행 붙여넣기·모바일 입력·서버 presence가 다시 어긋난다.

## Backspace는 무조건 왼쪽 칸 삭제가 아니다

Backspace는 방금 수행한 작성 흐름을 거슬러 수정하는 데 많이 사용된다. 그러나 공간에는 전역 문자열이나 줄 끝이 없으므로, 세계의 다른 글을 검색해서 이전 행 길이를 추측해서는 안 된다.

선택한 규칙은 **현재 작성 흐름에서 실제로 수행한 문자 진행과 줄바꿈 이동을 기억**하는 것이다.

| 입력 순서 | 기대 결과 |
| --- | --- |
| `ABC`, Backspace | `C` 셀을 비우고 그 칸으로 이동. `A`, `B`, 이웃 셀은 유지 |
| `ABC`, Enter, Backspace | Enter 직전의 다음 입력 위치로 커서만 돌아감. 어느 셀도 지우지 않음 |
| `ABC`, Enter, `D`, Backspace, Backspace | 먼저 `D`를 비우고, 다음 Backspace는 Enter 이전 위치로 돌아감 |
| Enter, Enter, Backspace | 마지막 줄바꿈 이동 하나만 되돌림 |
| `ABC\nD` 붙여넣기 뒤 Backspace 반복 | 문자·줄바꿈을 같은 순서로 직접 입력한 경우와 같은 위치 이동·삭제 |
| 새 위치로 지도 탐색 후 Backspace | 과거 작성 위치로 되돌아가지 않고 왼쪽 칸에 속한 글자를 비움. 두 칸 문자는 시작 칸으로 이동 |
| 방향키 또는 Home 후 Backspace | 왼쪽 칸에 속한 글자를 비움. 두 칸 문자는 시작 칸으로 이동하며 활성 작성 기준은 유지 |
| 새 줄에서 Delete | 현재 셀이 속한 글자를 비움. 이전 행으로 이동하지 않음 |

이 규칙은 줄을 합치지 않는다. Enter로 생긴 것은 빈 행 데이터가 아니라 커서 이동이므로, 그 이동을 되돌려도 주변 내용의 좌표는 그대로다. 일반 셀 삭제에서 작성자를 소유권처럼 취급하지 않는다. 이 공개 세계에서는 타인의 글도 명시적으로 덮어쓰거나 지울 수 있다.

경로는 최근 4096번의 문자 진행·줄바꿈 이동만 보관한다. 기록을 다 거슬렀거나 수동 커서 교정으로 경로를 비운 뒤에는 왼쪽 칸을 대상으로 삭제한다. 그 칸이 두 칸 문자의 뒤쪽이면 시작 칸으로 돌아가 글자 두 칸을 함께 비운다. 이 기록은 실행 취소나 셀 소유권 기록이 아니다. 예전에 덮어쓴 내용을 복원하지 않으며, 이후 다른 사람이 덮어쓴 셀을 삭제에서 보호하지도 않는다. 4096이라는 한도는 메모리 사용을 제한하기 위한 조정 가능한 구현 선택이다.

## 같은 종류의 설계 오류 조사

| 항목 | 발견한 문제 또는 선택 | 대응 |
| --- | --- | --- |
| Enter와 paste의 newline | 같은 글이 입력 이벤트 묶음에 따라 다르게 배치됨 | 작성 기준을 유지하고 공통 입력 계획에 전달 |
| 모바일 줄바꿈 | keydown만 수정하면 native beforeinput/input 경로는 예전 규칙을 유지함 | 줄바꿈 의도를 동일한 처리 경로로 연결 |
| 줄바꿈 직후 Backspace | 방금 입력하지 않은 다음 행의 왼쪽 셀을 지움 | 직접 수행한 줄바꿈 이동을 먼저 되돌림 |
| 방향키로 오타 교정 | 이동마다 작성 기준을 재설정하면 마지막 글자 교정만으로 다음 행의 시작 열이 바뀜 | 활성 기준은 유지하고 역추적 경로만 비움 |
| 조합 확정 | Enter가 문자 확정과 줄바꿈을 동시에 실행할 수 있음 | 조합 중 키는 OS가 처리하도록 두고 최종 문자만 한 번 확정 |
| `historyUndo` / `historyRedo` | 비어 있는 보조 textarea의 기록이 세계 편집 기록인 것처럼 재삽입될 수 있음 | 세계의 버전·경쟁 쓰기를 고려한 undo가 정의되기 전에는 새 글로 해석하지 않음 |
| `insertReplacementText` | OS 치환 결과를 현재 커서 뒤에 새 글로 붙이면 교정 의도가 훼손됨 | 범위를 확정할 수 없는 일반 자동 치환은 미지원. IME가 유지된 최근 입력 문맥의 끝부분을 바꾸는 경로는 아래 규칙으로 교체 |
| 단어·행 단위 삭제 | 보조 textarea에 세계의 문맥이 없으므로 native 삭제 결과만으로 범위를 알 수 없음 | 지원하지 않는 의도는 명시적으로 무변경 처리. 모르게 한 칸 삭제나 재삽입으로 바꾸지 않음 |
| Shift+방향키·Home·End, 전체 선택 | 범위 선택 의도를 한 칸 이동으로 바꾸거나 빈 보조 입력창만 선택할 수 있음 | 세계 범위 선택 미지원 안내. 커서와 세계는 변경하지 않음 |
| 복사·잘라내기 | 빈 보조 입력창의 내용을 세계의 선택 범위인 것처럼 취급할 수 있음. Shift+Delete를 Delete로 처리하면 잘라내기 대신 한 셀 삭제가 됨 | 입력창의 복사·잘라내기와 해당 단축키를 미지원 안내로 연결. 도움말 등 다른 UI의 일반 선택·복사는 유지 |
| Home / End | 문서 편집기의 행 시작·끝을 세계의 0열·마지막 열로 치환하면 임의의 토러스 경계로 이동함 | Home은 로컬 작성 기준으로 이동. End는 정의되지 않은 행 끝을 추측하지 않음 |
| Tab | 웹 UI의 초점 이동과 공간 들여쓰기는 다름 | 키보드 Tab의 접근성 초점 이동은 유지. 붙여넣기 tab은 공백 4칸으로 해석하는 기존 규칙을 안내 |
| 자동 가로 진행 | 화면 폭에 맞춰 다음 행으로 접으면 줌·기기마다 글의 좌표가 달라짐 | viewport 기반 자동 줄바꿈은 도입하지 않음. 기존 토러스의 같은 행 순환은 유지 |

실행 취소나 치환을 무조건 구현하는 것이 이번 판단의 결론은 아니다. **의도를 이해하지 못한 입력을 다른 편집으로 조용히 바꾸지 않는 것**이 우선이다. 지원하지 않는 동작은 시도했을 때 안내하고 세계를 변경하지 않아야 한다. 후속 undo는 셀 버전 충돌과 타인의 후속 덮어쓰기를 어떻게 다룰지 별도 설계가 필요하다.

## 한글 조합: 네이티브 문맥을 유지한다

사용자가 한글이 낱자로 분리된다고 보고했다. 기존 검사는 이미 조합이 시작된 한 음절의 완료만 다뤘으므로 연속 입력의 정합성을 보장하지 못했다. 실제 Chromium CDP에서 `insertText('ㅎ')` 후 이전 범위를 `하 → 한`으로 조합 교체하자, 기존 앱은 `ㅎ한`을 두 위치에 남겼다. 앱이 첫 input 직후 textarea를 비워 OS가 교체할 원래 범위를 잃었기 때문이다.

| 대안 | 판단 |
| --- | --- |
| 매 input/음절 완료 때 입력창 비우기 | 구현은 단순하지만 OS의 조합 범위와 문맥을 끊음. 기각 |
| 앱에서 낱자를 모아 한글 조합기 구현 | 두벌식·세벌식·모바일 후보 선택·다른 언어를 앱이 다시 구현하게 됨. 기각 |
| textarea 내용을 세계의 문서로 동기화 | OS 문맥을 얻지만 문서 삽입·선택 범위를 공간에 잘못 적용할 수 있음. 기각 |
| **네이티브 문맥을 보존하고 확정된 끝부분의 변경만 공간 편집으로 변환** | **선택. OS가 조합하고 앱은 확인 가능한 최근 작성 경로에만 교체를 적용** |

textarea는 매 키와 조합 종료마다 비우지 않는다. 확정 문맥과 새 값을 grapheme 단위로 비교해 추가된 글자 또는 교체된 끝부분을 얻는다. 조합 미리보기는 해당 조합 범위에서 표시하고, 조합 종료 뒤의 companion input은 같은 내용을 다시 쓰지 않는다. 명시적인 공간 이동·편집 명령·일반 재동기화에서는 문맥 경계를 새로 잡아, 이전 위치의 늦은 조합 완료가 새 위치에 쓰이지 않게 한다. 다만 주소가 보존된 자동 크기 변경은 아래 조건으로 구분한다.

교체는 최근 로컬 작성 경로에서 연속된 문자 전이로 확인할 수 있는 최대 32개 grapheme으로 제한한다. 경로를 알 수 없거나 줄바꿈을 거슬러야 하거나, 중간 삽입·범위 선택처럼 주변 글을 밀어야 하는 요청은 일반 새 글로 바꾸지 않고 거부한다. 이 경로는 이전 버전 복원이나 소유권을 부여하지 않는다. 같은 공개 좌표에 뒤늦게 다른 사람이 썼다면 일반 덮어쓰기와 같은 경쟁 규칙을 따른다. 32개 한도는 현재 구현의 제한이며 제품 불변식이 아니다.

따라서 한글 조합에 필요한 최근 입력 교체의 지원과 일반 문서형 자동 교정·선택·undo의 지원은 구분한다. 후자는 계속 별도 설계가 필요하다. 실제 기기별 IME 이벤트 순서는 후속 검증 대상이다.

### 자동 크기 변경과 조합 문맥

첫 Railway 배포 후 공개 주소의 실제 검증에서 `ㅎ`를 `한`으로 고치는 데 실패했다. 재시도는 통과했고 그 사이 세계 epoch 변경을 확인했다. 이를 단서로 `ㅎ` 확정 뒤 주소가 그대로인 density resize를 넣어 `ㅎ한` 중복을 로컬에서 재현했다. snapshot을 받는 코드가 네이티브 문맥을 비우는 별도 원인을 확인했다. 조합 코드만 문맥을 보존해도 세계 갱신이 그 문맥을 무조건 초기화하면 같은 실패가 남는다.

현재 크기 정책은 빈 가장자리 영역을 추가하거나 제거하며, 점유 셀의 좌표를 재배치하지 않는다. 서버는 이런 성공한 변경에만 `preservesAddresses:true`를 표시한다. 클라이언트는 다음 조건을 **모두** 만족하는 `density-resize` snapshot에서만 네이티브 버퍼·조합 미리보기·작성 기준·역추적 경로를 유지한다.

- 기존 연결이 살아 있고 서버가 주소 보존을 명시했다.
- 확인 대기 중인 쓰기가 없다.
- 본인 session ID와 커서 좌표가 이전과 같다.
- 작성 기준 열과 역추적 경로의 모든 출발·도착 좌표가 새 세계 범위 안에 있다.
- 문자 진행·줄바꿈의 인접성도 그대로다. 예를 들어 128열에서 126→0으로 진행한 경로는 256열 확장 뒤 연결이 달라지므로 보존하지 않는다.

일반 sync·오류 복구·실제 위치 이동·미확정 쓰기가 있는 경우에는 이 예외를 적용하지 않는다. 알 수 없는 snapshot을 정상 조합으로 이어 붙이지 않는다. 보존한 조합을 확정할 때는 갱신된 세계와 epoch로 쓰며, 과거 epoch의 쓰기를 재생하지 않는다.

이 조건은 epoch 숫자 변화와 실제 작성 위치의 변화가 같은 일이 아니라는 구분이다. 향후 resize가 주소를 remap하는 방식으로 바뀐다면 서버가 같은 보존 표시를 보내서는 안 된다. 실제 수정 후의 재검증 결과는 [VERIFICATION.md](VERIFICATION.md)와 [배포 기록](DEPLOYMENT.md)에 남긴다.

## 문자 폭: 기본 칸 1개 또는 2개

바이트 수는 인코딩에 따라 달라지므로 표시 폭의 기준으로 사용하지 않는다. Unicode 17의 East Asian Width에서 W/F인 문자는 2칸, 반각·중립·ambiguous 문자는 1칸으로 처리한다. emoji presentation, 국기·키캡·ZWJ 표시 묶음은 2칸이며, 결합 부호는 기저 문자의 폭에 추가 칸을 붙이지 않는다. 단독 결합 부호는 사라지지 않도록 주소 가능한 1칸을 받는다.

예를 들어 `A한B`의 시작이 x=10이면 `A`는 10, `한`은 11~12, `B`는 13을 사용하고 다음 입력 위치는 14다. 한글·한자와 라틴 문자의 간격은 2:1이지만 실제 렌더링 글꼴은 Arial·플랫폼 한글 sans-serif 계열을 유지한다. 폰트 측정값이나 기기별 fallback 글꼴이 세계 좌표를 바꾸지 않는다. 기본 화면 칸은 12×30px이며 줌에 비례한다.

| 표현 방식 | 판단 |
| --- | --- |
| 저장은 한 칸, 그림만 두 칸으로 늘리기 | 이웃 글과 겹치고 입력·삭제·상대 커서의 좌표가 표시와 달라짐 |
| 문자마다 가변 픽셀 좌표 사용 | 글꼴·기기별 측정 차이와 정수 격자·토러스 주소의 결합이 복잡해짐 |
| **반각 기본 칸 + 두 칸 문자의 시작/연속 칸** | **선택. 서버·클라이언트가 동일한 정수 주소와 표시 폭을 사용** |

두 칸 문자는 시작 칸에 `{text, width:2}`, 다음 칸에 `{text:'', width:0, leadX}`를 둔다. 연속 칸도 점유된 칸이며, 위치 탐색으로 그 칸에 커서를 둘 수 있다. 어느 절반을 삭제하거나 덮어쓰든 기존 문자 두 칸을 같은 서버 트랜잭션으로 정리하고 새 내용을 배치한다. 다른 글의 좌표는 밀지 않는다. Backspace는 알려진 문자 경로에서 2칸을 되짚고, 경로 밖에서도 왼쪽 칸이 연속 칸이면 시작 칸으로 돌아가 지운다. Delete는 현재 커서 위치를 유지한다. 커서는 문자 전체 폭이 아니라 한 기본 칸을 가리키며 화면 중심에 남는다.

토러스 마지막 열의 시작 칸과 0열의 연속 칸도 한 글자다. 다만 세계 너비를 바꾸면 그 두 주소의 인접성이 끊어지므로, 현재 실험은 이런 글자가 있는 동안 너비 변경을 보류한다. 이를 영구적인 크기 적응 정책으로 확정하지 않았다.

기존 저장 글을 자동으로 두 칸으로 확장하면 이웃 내용을 지우거나 밀어야 할 수 있다. 따라서 이전 기록은 좌표·내용·버전을 유지하고 `width:1`로 읽는다. 새로 입력하거나 덮어쓴 글부터 새 폭을 사용한다. 저장 형식의 컬럼 추가와 백업·복구 조건은 [배포 기록](DEPLOYMENT.md)에 남긴다. 새 클라이언트는 `layout:2`를 보내고, 이전 입력 프로토콜은 새로고침 안내와 함께 거절한다.

## 관성 탐색과 입력의 경계

빠른 마우스·터치 드래그를 놓으면 최근 이동 속도에서 감속을 이어 간다. 즉시 멈추는 기존 방식보다 지도 탐색에 맞지만, 입력 위치를 지나치거나 입력 중에도 움직이면 글을 잘못 배치할 수 있다. 따라서 타이핑·IME 시작·새 포인터 조작·줌·GPS·좌표 링크·도움말·연결 중단·화면 크기 변경·탭 숨김은 남은 관성을 중단한다. 핀치를 마친 뒤 남은 손가락에 이전 드래그 속도를 재사용하지 않는다.

휠에는 같은 fling 공식을 추가하지 않는다. 트랙패드는 이미 OS가 감속한 후속 wheel 이벤트를 보내므로, 추가 관성은 이동량을 중복한다. 전달받은 픽셀 이동량만 짧게 평활화하고 총량을 유지한다. OS의 동작 줄이기 설정에서는 드래그 관성을 끄고 휠 이동도 즉시 전달한다.

초기 조정값은 최근 80ms의 속도, 감속 시정수 220ms, 최대 지속 1400ms, 휠 평활화 45ms다. 프레임률에 따라 이동 거리가 달라지지 않도록 시간 기반 감속을 사용한다. 긴 프레임 정지 뒤에는 남은 이동을 버려 복귀 시 점프를 막는다. 이 수치는 실기기 촉감 실험으로 조정할 수 있다. 카메라는 여전히 기본 칸 단위로 움직여 셀 중심과 화면 중심을 맞추며, 관성이 임의의 픽셀 위치에 별도 입력점을 만들지 않는다.

## 검증 기준과 남은 가정

기존 코드의 이벤트 분할 반례는 위에서 실제 실행했다. 새 구현의 실행 결과는 [VERIFICATION.md](VERIFICATION.md)에 기록한다. 아래는 이 설계에 필요한 검증 조건이며, 나열 자체가 통과 주장인 것은 아니다.

- 여러 행을 한 번 paste한 결과와 글자·Enter·모바일 newline 이벤트로 나누어 쓴 결과의 셀 좌표가 일치한다.
- Enter는 주변 셀·버전을 변경하지 않으며 presence와 화면 중심만 새 입력 위치로 이동한다.
- 작성 기준 열은 지도 탐색 때 새로 잡고 방향키 교정·줌·포커스·키보드 표시만으로는 바뀌지 않는다. 첫 작성 전 방향키는 예상 기준을 이동시킨다.
- `ABC`, ArrowLeft, `D`, Enter는 `ABD`를 만든 뒤 원래 기준 열의 다음 행으로 이동한다. Home은 현재 행에서 같은 기준으로 돌아간다.
- Backspace는 줄바꿈 경계에서 무관한 셀을 지우지 않는다. 붙여넣기·연속 빈 줄·가로/세로 토러스 경계에서도 복귀 경로가 일치한다.
- 네이티브 한글 조합 확정과 companion input을 한 번만 기록한다. 조합 중 탐색·주소 보존이 확인되지 않은 epoch 변경 후 늦은 완료는 새 위치에 쓰지 않는다.
- 지원하지 않는 undo/redo/범위 불명 치환/범위 삭제·선택·잘라내기가 세계를 수정하지 않는다. 특히 Shift+Delete는 단일 셀 삭제가 되지 않는다.
- 결과가 확정된 같은 epoch의 재연결은 작성 기준을 유지한다. 주소 보존 조건을 만족한 자동 resize는 조합 중이거나 첫 자모가 확정된 뒤에도 입력 문맥을 유지한다. 불확실한 전송·일반 재동기화·오류 복구·주소 보존이 확인되지 않은 epoch 변경은 과거 문맥을 재사용하지 않는다.
- 첫 낱자 뒤 기존 범위를 바꾸는 조합이 `ㅎ한`처럼 중복되지 않고, 연속 음절과 늦은 companion input에서도 결과가 일치한다.
- 한글·한자·emoji의 2칸과 영문·숫자의 1칸이 서버와 렌더링에서 일치한다. 두 칸 문자의 어느 절반을 수정해도 고아 연속 칸이 남지 않는다.
- 관성 중에도 중심 커서와 상대 위치가 일치하고, 입력을 시작하면 즉시 관성이 멈춘다. OS wheel 이동량을 중복 증폭하지 않는다.
- 독립 클라이언트가 같은 변경과 커서 위치를 관찰한다.

지도 탐색을 새 장소 선택으로, 방향키를 현재 글의 교정으로 보는 것은 사용자 연구로 확정된 사실이 아니라 기본값에 대한 가설이다. 방향키로 멀리 이동해 새 글을 쓰거나 지도를 움직여 기존 글을 고치는 경우에도 이해되는지 관찰해야 한다. 이것은 소유 문단이나 영구 줄 경계를 만드는 규칙이 아니며, 관찰 결과에 따라 바꿀 수 있다. 실제 iOS/Android 키보드의 후보 확정·자동 교정·삭제 이벤트 순서는 기기별로 추가 검증해야 한다. 브라우저 에뮬레이션을 실제 휴대폰 검증으로 주장하지 않는다.
