## 이번에 다시 확인한 범위

깨끗한 후보 커밋, Node 24.22.3, CPU 할당 4코어에서 서버와 발생기를 별도 프로세스로 실행했다. 각 단기 시험은 512×256 세계, 160×48 시야, 실제 SQLite 파일과 WebSocket, 독립적인 루프백 접속 주소, 고정된 세계 시계를 쓴다. 발생기는 입력 확인(ACK)을 기다리지 않고 예정 시각에 다음 행동을 보낸다. 관측 묶음은 50ms이고, 참여자별 행동은 초당 한 번이다. [실행한 발생기](https://github.com/neocjmix/textworld/blob/f91a014e4987c406b8accdf6005e6225cb8be003/experiments/capacity.mjs)

| --- | ---: | ---: | ---: |
| 같은 지역 32명 전원 입력 | 1 | 53.6ms | 54.4ms |
| 같은 지역 48명 전원 입력 | 1 | 53.2ms | 54.0ms |
| 128명 중 6명 입력 | 1 | 57.7ms | 58.7ms |
| 두 지역 32명 입력·이동 | 1 | 53.5ms | 54.4ms |
| 조밀한 시야 16명 입력·이동 | 3 | 53.4~55.1ms | 54.1~57.3ms |

7회 합계 1,992개 행동을 보냈고 1,992개 ACK를 받았다. 예상 시야 변경 수와 수신 수는 64,512건으로 일치했다. 이 고정 배치에서 확인 가능한 글자 버전 누락, 시야 밖 글자 전달, 관측 순번 공백·역행, 429, 연결 종료와 배출 후 대기는 모두 0이었다. 11월 18일의 조밀한 시야 세 표본 중 한 번은 123.5ms였다. 비교할 때는 각 실행의 결과를 보존한다. [이번 단기 시험 원자료](measurements/stage1-review-short-2026-11-26.json)

같은 후보에서 32명을 두 지역에 배치해 실제 시계로 4분간 입력과 이동을 섞었다. 7,680개 행동 전부가 ACK를 받았고 처리 대기·순번 공백·연결 종료는 0이었다. 서버 전송 준비 p95는 53.0ms, 다른 클라이언트의 글자 디코딩 p95는 54.4ms였다. 세계 배치 버전은 2에서 9로 바뀌었고 관측자는 snapshot/reset을 총 224회 받았다. 10,114글자가 만료됐고 공유 시간 표식 기준 만료 나이 p95는 190.6초였다. 종료 표본에는 정리 대상 5글자가 남아 있었다. 이 실행에서 다른 참여자가 수신한 쓰기 버전은 76,800건이다. 움직이는 시야에서 기대 수신자 전부와 대조하는 항목은 아래의 후속 시험에 남는다. [4분 실제 시계 원자료](measurements/stage1-review-live-2026-11-26.json)

후보의 Node 회귀 검사 252개와 실제 Chromium의 타이핑 검사 9개, CJK 검사 10개가 통과했다. 같은 장비에서 비교한 기준 버전 `2eec724`와 후보 양쪽에서 키보드 열기·닫기의 중간 프레임 검사가 실행에 따라 실패했고, 이동 중 커서의 0.1픽셀 정렬 검사도 두 버전에서 실패했다. 실제 기기에서는 키보드 개폐 중 글자가 가려지는지, 정착 후 표시 위치와 입력 주소가 일치하는지 확인할 필요가 있다.

11월 18일 Railway 시험에서는 32명이 한 시간 동안 115,200건을 입력했고, 다른 31명에게서 3,571,200개의 쓰기 버전을 관측했다. 서버 전송 준비 p95는 53.8ms였다. 시험 서비스 한 대 안에서 통신했고 SQLite는 임시 디스크를 썼다. 같은 줄을 계속 덮어쓰자 초기 글자가 만료된 뒤 세계가 작아졌다. 넓은 세계의 여러 줄에서 글자가 늘어날 때의 저장량, 운영 볼륨의 동기 쓰기 지연, 인터넷을 통한 화면 표시 시간에는 각각 다른 측정이 필요하다. [Railway 시험 기록](https://github.com/neocjmix/textworld/blob/f91a014e4987c406b8accdf6005e6225cb8be003/docs/measurements/stage1-railway-2026-11-18.json)

## 무엇을 성공으로 셀 것인가

직접 지도에 들어가 체험할 때는 사용자의 시작 요청에 따라 프로덕션 러너를 가동한다. 봇마다 수명이 있고 인원을 줄인 뒤에도 만료와 축소가 계속된다. 체감 메모, 단계별 실제 인원, 세계 크기, 서버·브라우저 계측을 같은 시각으로 맞출 수 있다. 일정한 제공률의 포화 시험은 아래 절차로 실행한다. [체험 러너와 한도](PLAYTEST_RUNNER.md)

- **입력과 관측.** 예정된 행동 수, 실제 송신 수, ACK·거부·미처리 수를 맞춘다. 시야 안에서 공개된 글자와 커서는 받는 사람별로 중간 변경까지 순서대로 대조한다. 입력자가 자기 화면에 바로 그린 글자는 다른 사람이 받았다는 증거에서 제외한다.
- **시야가 움직일 때.** 소규모 합성 세계에서 확정된 쓰기·삭제·커서 이동과 당시 세계 크기, 관측자 위치를 기록한다. 시험 쪽에서 토러스의 시야를 직접 순회해 각 관측자에게 보여야 할 순서를 계산한다. 두 칸 글자의 한쪽이 시야 경계에 걸리면 유효한 짝까지 포함한다. 실제 서버의 구독자 선택 함수를 재사용하면 같은 필터 오류가 양쪽에서 가려질 수 있다. 기대열에서 하나를 빼거나 순서를 바꾼 대조 표본도 검사기가 잡아야 한다.
- **기준 화면 복구.** 성장·축소에 따른 정상 snapshot, 관측 순번 공백, 느린 소켓 종료, 재접속을 원인별로 센다. 끊기기 전에 받은 사건과 새 기준 화면 이후의 사건을 검증한다. 후보는 순번 공백에 snapshot을 요청한다. 그 사이의 기록을 재생했다고 집계하려면 실제 기록과 수신열을 대조해야 한다. HTTP/MCP의 턴 결과는 해당 API가 약속한 최종 시야와 부분 실행·429를 검사한다.
- **지연과 적체.** 같은 장비와 시야, 행동 제한, 50ms 묶음에서 정상 시야 변경 누락 0, 입력 처리 시작→전송 준비 p95 100ms 이내, 지속적으로 커지는 대기열 없음이 초기 목표다. 예정 시각→송신, 송신→ACK, 다른 클라이언트의 디코딩, 실제 브라우저의 그리기를 따로 기록한다. p99·최대값·부하 종료 시 대기와 배출 시간도 남긴다. 서버 이벤트 루프에 들어오기 전 대기는 예정 시각 기준 지연에서 드러난다.
- **미측정 구간.** 현 발생기는 고정 시계의 짧은 경로에서만 기대 시야를 계산한다. 실제 시계 시험의 `missingVisibleWriteDeliveries`와 `outsideViewWriteDeliveries`에 저장된 `null`은 ‘미측정’이다. 순번이 연속이어도 서버가 처음부터 잘못 고른 수신자는 발견할 수 없다. 동적 시야 검증을 통과한 뒤 이 항목을 0으로 판정한다.

32/48명은 실제 운영 피크를 집계하기 전의 비교점이다. 최근 운영 피크에서 동시에 보던 수, 실제 입력·이동률, 지역별 시야 중첩, 새 칸 증가율을 얻으면 해당 분포와 한 축을 1.5배 늘린 경우를 재현한다. 연결·전송만 포화하면 접속 서버 1대와 2대를 비교한다. 여러 지역의 쓰기·정리가 포화하면 세계 처리자 1대와 2대를 비교한다. 같은 지연 목표에서 한 시간에 빠짐없이 처리한 행동 수, 참여자 한 명이 한 시간 머무는 데 든 비용, 그중 외부 송신 비용을 기록한다. 고정 용량에서 수동 증감이 얼마나 자주 필요했는지와 그 비용 차이로 자동화 도입을 판단한다.

장시간 시험의 초기 판정 단위는 5분이다. 각 구간의 제공량·ACK·대기열·p95와 종료 후 배출 시간을 기록한다. 대기열이 연속 세 구간 증가하면 부하를 더 올리지 않고 발생기 지연, 전송, 세계 처리 중 어디에서 밀리는지 확인한다. 만료 표식의 현재 5초 단위를 고려해 만료 나이 p95 200초를 첫 비교 목표로 둔다. 후반 30분에는 살아 있는 칸 수가 비슷한 구간끼리 이력 행 수와 사용 페이지를 비교한다. 세계가 커지며 필요한 저장량과 이미 죽은 내용 때문에 누적되는 저장량을 구분할 수 있다.

## 재현과 비용 통제

후보 커밋을 별도 작업 디렉터리에 체크아웃하고 Node 24에서 다음을 실행한다. 마지막 명령은 로컬 자식 서버와 임시 SQLite만 사용한다. 12초는 입력 제공 구간이고 60초는 프로세스의 전체 실행 제한이다.

```sh
npm ci
npm test
npm run test:typing
npm run test:cjk
CAPACITY_CASES='[{"peers":32,"active":32,"rate":1,"layout":"uniform","action":"type","batch":true}]' \
  CAPACITY_DURATION_MS=12000 CAPACITY_OUTPUT=artifacts/review-32.json \
  timeout --kill-after=5s 60s node experiments/capacity.mjs
```

고정 시계의 정상 부하 결과는 아래처럼 검사한다. 기대 수신자를 계산하지 못한 표본의 `null`도 검사에 걸린다. 발생기 종료와 적용 성공을 구분해야 느린 클라이언트의 누락이 가려지지 않는다.

```js
// 후보 디렉터리에서 node --input-type=module 로 실행
import assert from 'node:assert/strict';
import { readFileSync } from 'node:fs';
const { results } = JSON.parse(readFileSync('artifacts/review-32.json', 'utf8'));
assert.ok(results.length > 0);
for (const row of results) {
  assert.ok(row.sent > 0 && row.acks === row.sent);
  assert.ok(row.expectedViewRecords > 0 && row.viewRecords === row.expectedViewRecords);
  assert.ok(row.readyCount > 0 && Number.isFinite(row.readyP95Ms) && row.readyP95Ms <= 100);
  assert.deepEqual(row.errors, {});
  for (const key of ['pendingAfterDrain', 'disconnects', 'uncorrelatedWriteAcks', 'ownMissing',
    'missingVisibleWriteDeliveries', 'outsideViewWriteDeliveries', 'revisionGaps', 'revisionRegressions', 'resets'])
    assert.equal(row[key], 0, key);
}
```

유료 시험 전에는 워크스페이스의 현재 사용액·Compute Hard Limit·이메일 알림 금액을 읽고, 시험에 허용한 시간·인스턴스·외부 송신 바이트를 정한다. Textworld의 워크스페이스 ID를 `TEXTWORLD_WORKSPACE_ID`에 지정하면 아래 명령으로 조회할 수 있다. 대시보드에서는 해당 워크스페이스의 Usage → Set Usage Limits → Compute Usage를 연다. Compute Hard Limit에 도달하면 그 워크스페이스의 워크로드가 중단된다. 이메일 알림은 통지만 보낸다. Railway Agent 한도는 Railway의 AI 사용료에 적용되고, Textworld에 접속하는 봇의 CPU·메모리·저장·송신은 Compute에 포함된다. [Usage 화면](https://railway.com/workspace/usage) · [비용 제어](https://docs.railway.com/pricing/cost-control) · [CLI 명령](https://docs.railway.com/cli/usage)

```sh
railway usage --workspace "$TEXTWORLD_WORKSPACE_ID" --json
railway usage limit status --workspace "$TEXTWORLD_WORKSPACE_ID" --target workspace --json
```

출시 전 사용자가 보는 부하 시험은 기존 프로덕션 월드에서 명시적 요청으로 시작한다. 현재 배포 버전·시간·인원·바이트 예산을 기록하고 종료 뒤 봇 퇴장, 처리 대기, 운영 비용을 확인한다. 고정 시계나 재시작을 통제해야 하는 벤치마크는 독립적인 로컬 재현으로 실행한다. [프로덕션 체험 운영](PLAYTEST_RUNNER.md)
