# Railway에서의 실제 수평 확장

2026-11-16. 현재 설정과 공식 문서를 확인한 **배치 설계**다. 이번 조사에서 Railway 설정을 변경하거나 새 인스턴스를 만들지 않았다.

공개 앱은 서비스·볼륨 각 1개를 사용한다. 접속 서버 분리, 세계 서버 분할, 자동 용량 조절은 각각 병목과 운영 필요가 확인될 때 진행한다. [트래픽 수준별 단계](SCALING_ROADMAP.md)

## 가능한가

**가능하다.** [최종 설계](FINAL_ARCHITECTURE_PROPOSAL.md)의 서버 확장은 독립적인 Railway 서비스/배포 인스턴스를 추가해 CPU·메모리·연결 처리량을 분산하는 인프라 수평 확장을 뜻한다. 같은 프로세스 안에 논리적인 구역 이름만 늘리는 것을 수평 확장의 증거로 세지 않는다. 물리 호스트 배치는 Railway가 관리하므로 인스턴스 수만 보고 서로 다른 물리 호스트나 장애 영역에 놓였다고 가정하지 않는다.

세계 확장과 서버 확장은 별개다. 세계 확장은 밀도에 따라 칸과 좌표 배치를 바꾸는 일이다. 서버 확장은 실제 처리량과 자원 사용량에 맞춰 인스턴스를 늘리는 일이다. 작은 세계도 매우 바쁘면 여러 서버가 필요하고, 큰 빈 세계는 적은 서버로 처리할 수 있다.

- `node server/index.js` 실행, 메모리 세계와 SQLite를 한 프로세스가 관리.
- 운영 소스는 `29045ba95c0f2031cfd726a6dbb5971b71c8c058`에 고정되어 있음.

이는 플랫폼 설정 조회 결과이며 이번에 새 부하 시험이나 장애 복구 검사를 한 것은 아니다. 현재 앱을 그대로 여러 개 실행하면 같은 세계의 처리 권위와 메모리 상태가 자동으로 공유되지 않는다.

## Railway에 대응시키는 방법

| Textworld 역할 | Railway 배치 | 증가 방법 |
| --- | --- | --- |
| 접속 서버 | 영구 볼륨 없는 `gateway` 서비스 | 같은 서비스의 replicas를 2→4→…로 추가 |
| 세계 서버 | `world-001`, `world-002` 등 별도 서비스. 같은 코드, 서로 다른 담당자 ID와 저장소 | 서비스를 추가하고 일부 공간의 담당을 이전 |
| 내부 중계 | 별도 서비스 또는 초기의 내부 스트림 | 구독/송신량에 따라 분할. 전역의 모든 변경을 한 병목으로 모으지 않음 |
| 소유권·배치 관리와 복구 기록 | 별도의 작은 제어/저장 계층 | 사용하는 저장 기술의 복제·분할 규칙에 따라 구성 |

처음에는 같은 프로젝트·같은 환경·같은 리전에 둔다. `world-001.railway.internal` 같은 내부 DNS로 특정 담당 서비스에 연결한다. 공개 트래픽의 무작위 부하 분산에 어느 구역의 담당자를 고르는 일을 맡기지 않는다.

세계 서버 하나가 여러 작은 논리 구역을 맡는다. **구역마다 Railway 서비스나 볼륨을 하나씩 만들지 않는다.** 영구 볼륨을 쓰는 세계 서버는 자기 볼륨을 가지며, 현재 SQLite 파일을 여러 서버가 공유하는 방식은 사용하지 않는다. 데이터 복제와 담당자 장애 복구는 애플리케이션/저장 계층에서 별도로 구현해야 한다.

## 반드시 반영할 플랫폼 조건

1. **수평 확장은 기본적으로 수동 설정이다.** Railway는 CPU·메모리를 플랜 한도 안에서 자동으로 조절하고, 수평 확장은 replicas 수를 설정하는 방식으로 설명한다. 입력량에 맞춰 인스턴스를 추가·제거하는 정책과 공간 재배치는 별도 자동화가 필요하다. 처음에는 고정 인스턴스 수로 검증한다.
2. **볼륨이 붙은 서비스는 replicas를 사용할 수 없다.** 공식 볼륨 문서의 제한이다. 그래서 접속 서버는 볼륨 없이 복제하고, 로컬 저장소가 필요한 세계 서버는 별도 서비스로 늘리는 안을 택한다. 대안은 세계 worker의 영구 상태를 분리된 저장 계층에 두는 것이지만, 그 저장 계층의 병목·복구도 함께 검증해야 한다.
3. **Sticky session을 지원하지 않는다.** 새 HTTP 요청과 재접속이 이전과 다른 gateway로 갈 수 있다. WebSocket이 유지되는 동안의 통신과 재접속을 구분하고, HTTP/MCP 세션·커서·순번·속도 제한의 권위를 gateway 메모리에만 두지 않는다. 어느 gateway에서도 같은 참여자 담당자를 찾아야 한다.
4. **볼륨을 가진 서비스의 재배포에는 짧은 중단이 있다.** 세계 서버의 무중단 인계는 Railway replicas 버튼만으로 제공되지 않는다. 복제된 상태, 유효 소유권 이전, 옛 담당자 쓰기 차단, 커서/관측 복구가 필요하다. 서버 두 개를 띄우는 첫 실험은 고가용성 완성으로 세지 않는다.
5. **수량 제한을 확인해야 한다.** 확인한 공식 문서는 프로젝트별 볼륨 한도를 Hobby 10개, Pro 기본 20개(증설 가능)로 안내한다. 현재 계정의 플랜명과 개별 증설 승인은 이번 조회로 확인하지 않았다. 서비스/replica/볼륨 한도와 사용량을 실제 증설 전에 점검한다.

Railway의 replica는 같은 앱을 여러 인스턴스에서 실행하는 기능이다. Textworld의 글자 상태 복제, 커서 인계, shard 배치와 같은 기능을 자동으로 제공하는 것은 아니다.

## 인스턴스가 늘어날 때 Textworld가 할 일

새 세계 서버를 띄우고 담당자 목록에 등록한다. 옮길 공간의 기준 상태와 그 이후 변경을 전달해 따라잡게 한 뒤, 소유권 세대를 바꾸고 옛 담당자의 쓰기를 차단한다. 접속/참여자 담당자는 새 소유자에게 입력을 전달한다. 축소할 때도 맡은 공간과 연결을 넘긴 뒤 종료한다. 관련 없는 공간의 입력은 계속 처리한다.

이 절차가 없으면 인프라 인스턴스만 늘고 같은 세계의 처리 용량은 늘지 않는다. A안의 단일 칸 판정 한계도 Railway로 옮긴다고 사라지지 않는다.

## 단계에 맞춘 실제 인프라 검증

먼저 단일 앱에서 변경 묶음·시야별 갱신·저장 수명을 개선하고 재측정한다. 실제 분리가 필요해지면 운영과 분리된 실험 환경에서 해당 단계만 확인한다.

1. **관객/연결 대응:** 볼륨 없는 gateway를 replicas 2개로 실행하고, 세계 서비스는 1개로 유지한다. 두 브라우저의 연결을 서로 다른 gateway에 배치해도 같은 글자·커서가 보여야 한다. 한 gateway 재시작과 HTTP/MCP 요청의 다른 인스턴스 도착도 검사한다.
2. **세계 처리 분산:** 세계의 쓰기/정리/상태량이 병목이면 별도 세계 서비스 2개를 같은 리전에 배치한다. 각각 별도 저장소를 사용한다. 고정 담당표로 시작하되 수동 공간 이전, 경계 CJK, 조합 중 크기 변경, 짧은 기록 이어받기는 안전해야 한다. 복제·장애 복구는 별도 실패 주입으로 검증한다.
3. **분산 효과 확인:** 실제 세계 서비스 수를 1/2/4/8개로 늘려 같은 단위 부하를 추가한다. 각 인스턴스의 자원 한도와 관측 주기를 동일하게 유지하며, 접속/중계 계층이 먼저 포화되는지도 분리해서 기록한다. 물리 호스트 배치 차이는 보장하거나 고정했다고 가정하지 않는다.
4. **운영 자동화:** 수동 증설/재배치가 반복될 때 제어기의 판단만 먼저 기록하고, 검증한 증설·인계부터 자동화한다. 안전한 축소는 이후 검증한다. 자동 제어기 구현을 첫 분산 실험의 선행 조건으로 삼지 않는다.

모든 단계에서 CPU·메모리·기록 저장량·실제 외부 송신량과 ACK/관측 지연을 같이 측정한다. 같은 머신의 프로세스 수만 늘린 결과를 Railway 수평 확장 실측으로 보고하지 않는다.

공식 문서는 private networking의 내부 트래픽을 egress 과금에서 제외한다고 안내한다. 브라우저로 보내는 외부 트래픽, 추가 인스턴스의 CPU·메모리, 볼륨 비용은 남는다. 현재는 새 구조의 비용/수용 인원을 계산할 실측 데이터가 없다.
